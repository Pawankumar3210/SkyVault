# Google Cloud setup

Cloud Mode is implemented but requires an owner-provided GCP project, service account, and bucket. No real cloud operation has been verified without those credentials.

## 1. Project and Firestore

1. Create or select a Google Cloud project.
2. Enable the Cloud Firestore API and create the **default** Firestore database. Choose a location near the bucket; database location cannot be changed after creation.
3. Deploy the checked-in indexes with `gcloud firestore indexes composite create` or the Firebase CLI. The project includes `firestore.indexes.json`.
4. Apply `firestore.rules`. These rules deny direct client reads and writes; all application access goes through the server-side Admin SDK.

## 2. Private Cloud Storage bucket

Create a Standard class bucket in `us-central1`, with Uniform bucket-level access and Public access prevention enforced. Do not grant `allUsers` or `allAuthenticatedUsers` bucket/object access. Configure the bucket's CORS for the exact local/deployed web origin and `PUT`, `GET`, `HEAD` methods with `Content-Type` as a request header; signed URLs do not override browser CORS policy. Use unique object prefixes generated by Sky Vault.

The workspace storage limit is a product warning, not a hard GCS quota or billing guarantee. Check Google Cloud Storage usage and Cloud Billing regularly. Do not enable paid services automatically.

## 3. Service account

Create a dedicated server service account. Grant the minimum roles needed to read/write Firestore and create/use signed URLs for the single bucket (typically a narrowly scoped Firestore role and object create/view/delete permissions scoped to that bucket). The account needs signing capability for v4 URLs; use IAM service account signing permissions if applicable to the chosen keyless setup. For JSON key configuration, store the key only in a secret manager or Vercel encrypted server environment variable. Never commit it or expose it through a `VITE_` variable.

## 4. Local environment

Set the following in local `.env` for the API, and `VITE_APP_MODE` in `.env.local` for Vite:

```dotenv
APP_MODE=cloud
VITE_APP_MODE=cloud
GCP_PROJECT_ID=your-project-id
GCS_BUCKET_NAME=your-private-bucket
GCP_REGION=us-central1
GOOGLE_APPLICATION_CREDENTIALS_JSON={"type":"service_account",...}
MAX_FILE_SIZE_MB=10
WORKSPACE_STORAGE_SOFT_LIMIT_MB=500
UPLOAD_WARNING_PERCENTAGE=70
UPLOAD_URL_EXPIRY_SECONDS=300
DOWNLOAD_URL_EXPIRY_SECONDS=900
MAX_RETAINED_VERSIONS=5
PENDING_UPLOAD_TTL_SECONDS=3600
BACKUP_RETENTION_DAYS=7
CORS_ALLOWED_ORIGIN=http://localhost:5173
```

JSON must be a single valid value. The server validates required configuration at startup/API health. Restart the API after changes. Local Cloud Mode needs bucket CORS to allow `http://localhost:5173`.

`PENDING_UPLOAD_TTL_SECONDS` controls when abandoned uploads are eligible for cleanup; keep it longer than `UPLOAD_URL_EXPIRY_SECONDS`. `BACKUP_RETENTION_DAYS` controls how long pre-action workspace snapshots stay in the `workspaceBackups` Firestore collection.

The maintenance cleanup needs `storage.objects.list` and `storage.objects.delete` on the bucket, in addition to the upload/download signing permissions. A backup snapshot is a single Firestore document, so keeping retention short and workspace records bounded avoids the 1 MiB per-document limit.

## 5. Verify Cloud Mode

Check `GET /api/health` and verify mode `cloud`, configuration status `true`, and storage `gcs`. Then create a test subject, upload a small permitted PDF, reload, download it, replace it, and inspect document versions. Remove test records/files afterward. Do not claim cloud verification until these real operations succeed.

With real credentials configured for the API process, run `npm run test:cloud`. The script refuses to run unless `APP_MODE=cloud` and all configuration checks pass. It verifies the bucket exists, performs a small Firestore write/read/delete round-trip in the `smokeTests` collection, generates v4 signed upload and download URLs without printing them, and runs `POST /api/maintenance/cleanup` logic. It prints one `PASS` or `FAIL` line per check and exits nonzero on any failure. Do not run it without credentials, and never claim it passed unless you ran it yourself against the intended project. Cleanup may delete genuinely stale objects under the server-generated `pending/uploads/` prefix.

## 6. Usage and cost checks

Review GCS storage, operations, network egress, Firestore reads/writes/storage, and the Cloud Billing console. Google Cloud free-tier eligibility and pricing can change; no zero-cost guarantee is made. Keep the single default database, small file cap, bounded versions, and efficient access patterns. Configure billing budgets/alerts in the GCP account if desired; Sky Vault does not activate paid products or billing plans.
